> ## Current-source audit — 2026-11-27
>
> This document contains historical implementation narratives. Where they disagree with
> the current source audit below, this section is authoritative until the corresponding
> ticketed implementation and client witness land. A description of an intended rule is not
> evidence that the runtime enforces it.
>
> ### Ownership and package lineage
>
> Popit Shell is the modern Windows desktop and OTA phone client/application implementation
> of Secure Shell and Restore. Its current client app signing and store are retained; they are
> not replaced by a second Restore writer. The current Popit package writer/digest reader is
> `dialin.py`, the app manifest/publisher is `app_package.py`, the mutable Settings package
> is `settings_package.py`, and the signed app-base mutation is `app_base.py`.
>
> `dialin.PACKAGE_SCHEMA` is generated by `format_id("secure-shell.package", ...)`; the
> BLAKE3 digest domain uses that generated schema identifier. It is not proven byte-for-byte
> identical to Restore's reference module's literal `b"secure-shell.package/1"` domain.
> Do not describe Popit's digest as the literal Restore digest without a compatibility
> vector. Popit's format is the current client implementation; any change or adapter must
> be ticketed, versioned and tested. No second reader/writer and no automatic legacy fallback.
>
> Restore names the Debian server as the package-stream signing authority. Popit currently
> signs its client app package records with the Settings publisher's Ed25519 key, trusted
> through the Popit registry used by its phone client. These are distinct trust roles today.
> The cross-host trust/admission relationship between Debian's streamed package assertion
> and Popit's Settings publisher assertion must be explicitly bound by the Restore/Popit
> contract; do not silently reuse a key, equate the authorities, or treat TLS as a package
> signature. BLAKE3 identity, Ed25519 signature, admission, stream, mount receipt and client
> witness remain separate claims.
>
> ### Corrections to current implementation claims
>
> - **Dependency pins:** `app_base.subscription()` embeds the current Settings identity,
>   digest, payload digest and control/project baselines in the signed app payload.
>   `app_package.publish()` nevertheless writes app manifests with `dependencies: []` and
>   emits `app-name@revision+blake3:...` without the Restore pin-complete dependency suffix.
>   The payload reference is not a substitute for the canonical manifest dependency set.
>   New/republished apps need a declared pin to the exact Settings identity.
> - **Kinds:** the current `app_package.KINDS` is `("window", "phone")`. The historical
>   `surface` description below is not a currently signable kind; bridge is a refused
>   foreign window page. A kind not in the current registry is not a package.
> - **What "subscribes" currently means:** app scripts call `attach("<name>")` from
>   `/package.js`; that reads `GET /api/toast/apps/<name>`, whose server path calls
>   `AppPackages.document()` and verifies the Ed25519 signature/trust before returning
>   `verified: true` over the HTTPS client origin. `app_base.subscription()` creates the
>   signed mutated Settings-base record carried by the app package. Separately,
>   `SettingsPackage.subscribe()` implements a signed window-key/nonce subscriber-admission
>   registry, but the current `ui/package.js` attach path does not call that method. These
>   two mechanisms must not be conflated; the actual admission handshake is a ticketed gap.
> - **Rendering and isolation:** the registered window apps still use `toast.html` as their
>   entry. `toast.py::app_page()` composes the Settings document/head with the whole body
>   from `toast.html`; this body contains DialIn, Settings, Prose, Archive and Evidence
>   panels, and `toast.js` contains their mode controllers. This is not yet an isolated
>   per-app body factory. App identity does not imply lifecycle isolation. Home/close must
>   deactivate the previous app, stop its timers/resources and remove its body before the
>   next surface is shown.
> - **UI audit is not a mandatory publication gate yet:** `AppPackages.publish()` records
>   `ui_audit: pending` when no audit exists. `verify()` can still return
>   `verified: true` for that record; it does not require `ui_audit == "passed"`. The phone
>   tile code uses `verified` and launch proof. Pending must become a hard non-launchable
>   state, with the audit tied to the exact payload digest.
> - **Launch proof is not the full client witness:** `launch_proof()` reads signed entry
>   bytes and source structure. It does not, by itself, prove the actual Qt/Windows or OTA
>   phone client mounted, rendered and behaved correctly.
> - **Signed asset closure:** the current app file lists include shared JS/CSS and app
>   documents, but separately served web manifests and icon assets are not all in those
>   per-app file lists. The phone/PWA asset trust boundary needs explicit inventory and
>   admission coverage; do not infer that a signed window payload covers every URL served
>   by the origin.
> - **Client verification:** `ui/package.js` fetches the app document and accepts the
>   server's `verified: true` result, then applies the Settings theme. The server performs
>   Ed25519/trust verification. The browser code is not an independent Ed25519 verifier;
>   secure-origin transport and server verification are part of the current trust path.
> - **Store meaning:** `tools/app_store.py` produces `docs/app-store.json` as a projection
>   of the live signed AppPackages registry. It is not a second authoritative package
>   store. The live registry/package verifier remains the source of truth.
>
> ### Required publication invariant
>
> A package is not launchable merely because its signature verifies. The signed identity
> must bind its complete declared dependency pins and served asset closure; the app must
> derive from the current Settings base; its exact payload must have a passing UI audit;
> the signed launch route must be proven; the authorized CUA driver/task receipt must be
> present; admission and client mount checks must succeed; and the actual Windows/Qt or OTA
> phone client must provide the required witness. Any missing item is absent/refused, never
> inferred from a CI badge or a source-level check.

# App packages

Every surface the shell serves is an app package: `dialin`, `settings`, `prose`, `archive`,
`evidence` and the `springboard`. The shape comes from the settings package and the phone's
security work, applied once rather than per page.

## What an app package is

An app names the files it serves (`app_package.APPS`) and hashes them into the family's
`secure-shell.package/1` identity. The record carries the identity, the payload digest and
the publisher's Ed25519 signature; it is signed with the settings package's key and
verified against `runlogs/toast/envelope-trust.json`, the same registry the phone and the
settings window read. There is one publisher (`popit-publisher`), not a second authority
per app.

An app is **authored**, not a folder of files. The signed payload is a `popit.app/2`
document: `kind` (`window`, `surface` or `phone`), the `entry` page, `title`, `summary`, the
`pages` the app adds, the `adds` list a reader can quote, and `derives` naming the settings
package and the fields it takes from it (`theme`, `layout`, `motion`, `dpi`). A payload that
only lists files is a **legacy package**: `verify()` refuses `app-legacy` before the tamper
comparison, and a document with an incomplete manifest is refused `app-not-authored`. That
is why the IDE could not pass as a hand-written page: its payload now says it is a `surface`
with sessions, turns, probes, drivers and bridge pages, and what it derives from settings.

## The signing forms, and the store

A mutable package may take only the three reference forms: `window` (dialin, settings) and
`phone` (springboard). A surface hosted inside a window is refused `app-kind-foreign` — the
IDE has no package identity of its own; dialin's manifest names it under `hosts`, and the
IDE page carries its host's identity and theme.

Every republish is a mutation and is attributed to the CUA driver that carried it: with a
fleet attached, a mutation without a live driver is refused `app-no-driver`, and the driver
is written into the signed record. `tools/app_store.py` builds `docs/app-store.json` for the
landing pages from the signed registry — five packages, their identities, their driver, and
the bridge's refusal — and refuses to write if a package is unverified or a foreign kind is
listed (`store-no-driver`, `store-unverified`, `store-foreign-package`).

A window package is also furniture. Every app declares four regions — `bar`, `status`,
`body`, `foot` — and the entry page must carry `data-region="…"` for each; a page with a
header and a list is refused `app-window-incomplete` rather than signed. Dialin is the
reference: a bar, the mode strip, the body and the foot that names the identity and theme.

The window ground and its scrollbars are the family's, not the browser's. `ui/package.js`
folds the published `deep` role into a dark ground (`groundFrom`, hue kept, light capped) and
writes `--popit-ground`; `ui/contour-theme.css` paints `html` and every scrollbar from it. A
default scrollbar or a page painted in the raw `deep` role is refused by the gate
(`scrollbars-are-themed`, `window-ground-is-the-published-ground`).

The identity is over the *served* files, not a build. If a file changes after the package
was published, `verify()` refuses `app-tampered` instead of serving the changed surface
under the old identity. `ensure()` republishes on the next start when the files moved on.

Refusals are named: `app-unknown`, `app-unsigned`, `app-tampered`, `app-identity`,
`app-signature`, `app-untrusted`, `app-file-absent`.

## Routes

| Route | Answer |
|---|---|
| `GET /api/toast/apps` | every app's identity and verification state |
| `GET /api/toast/apps/<name>` | one signed document: identity, files, signature, theme |
| `POST /api/toast/apps/verify` | the same document; `secure-origin-required` off TLS and off loopback |

`POST /api/toast/apps/verify` keeps the phone's posture: a signed identity is read over a
secure origin, and loopback is the machine itself.

## The two archive apps

`archive` and `evidence` are the legacy shell's session archive and evidence backup, rebuilt
as desk windows. Their old page was `ui/archive.html`; it polled a route the loopback server
never answered, and `/api/archive/*` pointed at dropped functions. Both files and routes are
retired, and the shell's server answers the old paths `archive-legacy-retired`.

Each app is kind `window`, entry `toast.html`, delivered in `popit-settings-package`, and
launched at `/toast.html?window=archive` or `?window=evidence`. Each carries the four
regions, a tile on the SpringBoard, a route in the window audit, and a launch proof read
from the bytes its payload signs. Both are built from two pinned baselines: the settings
window's signed delivery, and `app_base.PROJECT_SETUP`.

The project setup is the second baseline. It pins what every family project owes: a ticket
before the change, a named refusal, its own failure row, a ledger, a CI job, a landing page
rendered from its pins, a live driver on each republish, and copy read by the family
checker. The digest travels in the signed base, so a package built against another setup is
refused `app-project-baseline-stale`.

The rows come from `session_archive.py`. The index walks every local fixed or removable
drive in the background and caches under `runlogs/session-archive/` for an hour. A copy
writes source and record files to the evidence root and records a large asset by size and
time. A clean lists the four family cache trees and removes them only on the second
confirmation. Every act appends a row to `runlogs/session-archive/ledger.jsonl`.

| Route | Answer |
|---|---|
| `GET /api/toast/session` | the index, the evidence root and the recent rows |
| `GET /api/toast/session/files?slug=` | one project's files, up to the limit |
| `POST /api/toast/session/backup` | copy the selected project or all of them |
| `POST /api/toast/session/clean` | list the cache trees, or remove them with `apply` |
| `POST /api/toast/session/rescan` | start a fresh walk of every drive |
| `POST /api/toast/session/show` | open a project or the evidence root, loopback only |

A mutation is loopback or TLS, the same posture as `/api/toast/apps/ensure`. An act that
cannot be shown is refused by code: `archive-unknown-project`, `archive-backup-none`,
`archive-path-outside`, `archive-clean-confirm`, `archive-evidence-absent` and the rest.
`tools/session_archive_probe.py` measures the copy, the cache rule and the refusals on a
fixture project, and reads the live windows when the desk answers.

## The theme an app runs

A document carries `theme` and `theme_identity` from the settings package, so an app takes
the frame, material, motion, motion preference and DPI the owner published rather than a
private copy. `ui/package.js` is the shared client: it refuses a document that is not
verified, applies those attributes to `<html>`, and names the identity it is running. It
does not repaint a surface whose package it cannot verify.

`springboard` is the phone page the family already serves (`/phone.html`), loaded into the
shell when the SpringBoard frame is chosen. The phone's own footer names
`app-springboard@<rev>+blake3:<digest>`, and DialIn and Settings are tiles on that page;
they hand control back to the shell over `postMessage` rather than navigating it away.

## The bar is closed, and a package adds pages, never controls

A past revision shipped an `IDE` button in the desk's own bar and a hosted `/ide` page the
window loaded as a surface. Both are removed: `ui/ide.html|js|css`, `ide.py`,
`tools/ide_probe.py`, the `/ide`, `/ide.js`, `/ide.css` and `/api/ide*` routes, the
`#ide-chip` and `#ide-surface` nodes, the `ide` entry in the window's `SURFACES` map, the
`ide_url` in `bridge.py`'s target record, and the `FOREIGN = {"ide": "surface"}` slot in
`app_package.py`. The signable forms are `window` (dialin, bridge, settings) and `phone`
(the springboard); there is no surface kind to sign.

The defect was ownership, not the page: an app package had a control in the shell's bar, so
removing it meant editing the desk, and to a reader it looked like part of the window. Four
checks hold that line:

- `bar-controls-pinned` — the header carrying `data-region="bar"` holds exactly the shell's
  `settings`, `pin` and `close` buttons.
- `bar-no-app-surface` — no chip, app button or `<iframe>` sits in the bar.
- `status-strip-does-not-launch-an-app` — the status strip names state and holds no chip or
  app button.
- `no-app-bar-control` — a signed payload that names `bar_controls`, `chrome` or `controls`
  is refused `app-bar-control` before signing; `tools/app_package_probe.py` proves it with a
  planted payload.

The desk itself is not hand-rolled any more: the CUA drivers rebuild it from the signed
settings app package (wish `task-0003`), and `tools/freshness.py` carries that rebuild as the
stale row `dialin-rebuild` until it lands.

## Project convention: an app package subscribes to the settings app

The owner made this the convention for every app package from 2026-11-25: *"the new dialin
app package would subscribe to the settings app this is project convention from now on and
the app we use must be able to still sign it's packages properly where we bring in new
features/dependencies and development must be driven in the family byt the cua drivers"*.

A mutable package therefore does two things, and both are refused at signing time:

- **It subscribes.** A signed script calls `attach("<name>")` from `/package.js`; the frame,
  material, motion type, motion preference, the ten colour roles, its layout and DPI come
  from the verified settings document. A package whose scripts never attach is refused
  `app-not-subscribed` — a private theme copy is not a package.
- **It signs every asset it loads.** `/contour.js`, `/package.js`, `/contour-theme.css`,
  `/popit-sw.js`, a second script — each must be in the package's `files`. A page or script
  that loads a served `.js` or `.css` the package does not declare is refused
  `app-dependency-undeclared`, because it would render and be audited without being covered
  by the identity. `contour.js` and `phone-calls.js` were exactly that gap before this rule;
  they are declared now.

`tools/app_package_probe.py` proves both refusals with a throwaway surface (16 rows), and the
gate carries `packages-subscribe-the-settings-app`. Development of the packages themselves is
family work: the CUA drivers carry it (the desk's rebuild is wish `task-0003`), and
`tools/freshness.py` keeps every stale package, tile, audit, ledger, refusal, landing page and
CI row visible with the driver act that clears it.

## The surface audit

A package is signed only for a surface that can be drawn. `ui/ui-audit.js` measures the
rendered page and reports four refusals: `ui-overlap` (two visible controls on one box),
`ui-clipped` (a text surface hiding content it does not ellipsize), `ui-x-overflow` (a
phone-width page wider than the phone) and `ui-x-locked` (overflow no axis can reach).

A page opened with `?uiaudit=1&app=<name>` posts its report to `/api/toast/ui-audit`. The
server stores it against the payload digest, and `AppPackages.publish` refuses
`app-ui-audit` while that measurement reports findings. A surface nobody has measured
publishes with `ui_audit: pending`; a clean measurement gives `ui_audit: passed`. The
SpringBoard reads the same registry (`/api/toast/apps`), so its tiles exist only for signed
packages, carry the contour frame on the tile and the glyph, print their identity, and a
refused package is a disabled tile rather than a launch that fails later.

The shell root `/` is the SpringBoard. The desk is `/toast.html`, which is where the
pinned window and the DialIn tile point.

## Known limits

- A legitimate edit publishes with `ui_audit: pending` until the page is opened with
  `?uiaudit=1`, and reports `app-tampered` if the edit lands while the shell runs. Both
  clear on the next page load.
- DPI is one control: `--popit-dpi` and `data-dpi` name it, and the applied scale is
  `min(dpi, viewport / floor)` with a per-surface floor (`dialin` 400, `settings` 360,
  `springboard` 320). The desk hands its scale to the Qt bridge when the window exists and
  uses CSS zoom with a matching width elsewhere.
